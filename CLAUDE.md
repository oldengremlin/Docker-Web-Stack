## Мета проєкту (мірило для всіх рішень)

Працюючий web стек із **мінімальним ручним втручанням**.

## Це продакшн, а не полігон

Зафіксовано, щоб користувач не мусив нагадувати:

- Стек **уже працює на продакшн-сервері**. Проєкт не піднімають з нуля —
  його продовжують підтримувати. Будь-яка зміна оцінюється питанням
  «що це зробить із працюючими сайтами просто зараз».
- **Структура каталогів на хості вже є і не змінюється.**
  `/var/sites/<домен>/{web,db}`, `/var/sites/letsencrypt`. У шляхах нічого
  не ламаємо — ні на хості, ні всередині контейнерів.
- Бази даних мають продовжити працювати, сертифікати — продовжити жити.
  Імена БД, користувачів і паролі успадкованих доменів зберігаються як є,
  навіть якщо не збігаються зі схемою іменування.
- Контейнери доменів **відокремлені один від одного**. nginx — це лише
  фронтенд для них: https/http2/http3 і на цьому його роль закінчується.
  Не тягнути логіку доменів у nginx.
- Якщо щось таки змінюється кардинально — має бути **імпорт наявного
  стану з мінімумом ручної роботи**, і наслідки мають бути видимі **до**
  того, як їх застосують.

## Обов'язкове правило при кожному коміті

**Кожен коміт із змінами коду повинен містити також:**

1. **`CHANGELOG.md`** — новий розділ `## [X.Y.Z] — YYYY-MM-DD` з описом
   усіх змін (підрозділи: `### Додано`, `### Змінено`, `### Виправлено`)
2. **`README.md`** — оновлені розділи, що стосуються змінених функцій.
   Оновлюємо діаграми.

Це не опціонально. Якщо зміна коду є — документація оновлюється в тому
самому коміті.

## Версіонування

У `dcpmgmt` є `our $VERSION`. **При зміні коду версію оновлюємо
ОБОВ'ЯЗКОВО** — семантично (`X.Y.Z`):

- `Z` — виправлення, що не змінює поведінку для користувача;
- `Y` — нова команда, новий ключ, нове поле реєстру;
- `X` — зміна, яка вимагає ручних дій при оновленні (формат реєстру,
  розкладка каталогів, несумісна зміна `dcp.conf`).

Версія в `$VERSION`, заголовок у `CHANGELOG.md` і те, що реально в коді,
мають збігатися. `dcpmgmt version` — те, що покаже користувач у баг-репорті.

## Домен та стиль коду

- Назви методів і змінних — англійські; коментарі/логи — за потребою
- Не додавати зайвих абстракцій і обробників помилок без потреби
- Не писати коментарі, якщо `WHY` очевидний з коду, в усіх інших
  випадках коментарі — обов'язкові.
- Проміжні змінні вводити лише коли результат використовується двічі
  або вираз важкочитабельний; для ланцюжків внутрішніх методів проекту —
  уникати зайвих; для зовнішніх API/бібліотек — допустимі заради
  налагодження

## Непорушні правила

На кожен домен — своя структура. Не об'єднувати в Nginx. Це пов'язано з
тим, що Let's Encrypt сертифікати не підтримують вілдкард.

## Прийняті архітектурні рішення

Не переглядати без нової вагомої причини:

- **Реєстр `domains/*.conf` — джерело істини.** `docker-compose*.yml` і
  `nginx/*.conf` генеруються з нього. Генерація повна, не `sed`-патчинг
  наявних файлів: патчинг «перед першим рядком, що…» ламається від
  першої ж ручної правки структури.
- **Згенероване не перезаписується без `--force`.** Ручні правки на проді
  не мають зникати мовчки. Для правок, що мають пережити регенерацію, є
  `nginx/custom/<домен>.conf` і `.php.conf` — їх не чіпаємо ніколи.
  `docker-compose.domains/<домен>.yml` proxy-типу належить адміну навіть
  при `--force`.
- **Один спільний `certbot` на весь стек**, не по одному на домен.
  Первинна видача — разовий `docker run`, не `exec` у renew-контейнер.
- **Імена БД виводяться з домену детерміновано** і нічого не питається:
  крапки геть, дефіси лишаються (`www.ukr-com.net` → `wwwukr-comnet`,
  користувач `uwwwukr-comnet`, хост `db-wwwukr-comnet`). Так названі
  наявні продакшн-контейнери — сумісність навмисна.
- **Паролі — тільки в `secrets/<домен>.env`** (0600, поза git), у compose
  підключаються через `env_file`.
- **Паролі БД типово виводяться з домену**: HMAC-SHA512(майстер-ключ,
  домен). Ключ — поза проєктом (`~/.dcp-master-key`, 0400), створюється
  сам, не змінюється ніколи: зміна робить видані паролі невідтворюваними.
  Режим фіксується в реєстрі при створенні домену, успадковані домени —
  завжди `random`. Алгоритм продубльовано в `tools/mkpass`; змінюєте один
  — змінюйте обидва, інакше результати розійдуться.
- **Ім'я compose-проєкту зафіксоване в `dcp.conf`** і потрапляє в `name:`.
  Воно формує префікс імен volume'ів; зміна = нові порожні volume'и.
- **Тег образу WordPress: fpm обов'язковий, PHP фіксуємо, версію ядра —
  ні.** `wordpress:latest` — це апачевий образ (той самий digest, що й
  `wordpress:apache`); він не слухає FastCGI на `:9000`, тож дав би 502.
  Дефолт мейнтейнерів образу взагалі PHP 8.3 (`fpm` == `php8.3-fpm`).
  Тег вирішує дві різні речі: версію PHP, яка щодня виконує сайт, і
  версію ядра, яка ляже в **порожній** `web/` — у робочому каталозі ядро
  оновлює себе саме через адмінку. Тому `wordpress:php8.4-fpm`: PHP
  зафіксований (стрибок мажорної версії тихо ламає плагіни), ядро
  плаває. Не alpine: musl замість glibc — інший рантайм заради 160 МБ.
  `add` і `doctor` відхиляють не-fpm образ.
- **HTTP/3 не має заголовка `Host`** — лише псевдозаголовок
  `:authority`. nginx кладе його у `$host`, але fastcgi формує
  `HTTP_HOST` з `$http_host`, який лишається порожнім, і WordPress
  віддає canonical redirect на `https:///` (у Chrome
  `ERR_INVALID_REDIRECT`). Тому в шаблоні є
  `fastcgi_param HTTP_HOST $host;`, а `doctor` стежить за ним. Сайт зі
  сторінковим кешем маскує цю поломку: на головній PHP не запускається.

## Перевірка змін

`dcpmgmt` можна ганяти без docker-демона: `docker compose config` працює
клієнтськи. Мінімум перед комітом:

```bash
perl -c dcpmgmt
./dcpmgmt render && docker compose config -q     # на тестовій інсталяції
./dcpmgmt doctor
./dcpmgmt version                                # збігається з CHANGELOG.md?
```

Згенеровані nginx-конфіги перевіряються справжнім `nginx -t` — див.
історію сесії: пісочниця з підміненими шляхами до сертифікатів і
фейковими upstream-хостами в `/etc/hosts`.

Діаграми в README — mermaid, не псевдографіка. Синтаксис перевіряється
справжнім парсером, а не на око:

```bash
npm install mermaid jsdom
node -e 'import("jsdom").then(async ({JSDOM})=>{ ... mermaid.parse(block) ... })'
```

(робочий скрипт — в історії сесії; головне, що перевірка існує і що
неперевірену діаграму в README класти не можна)
